# 部署、迁移与恢复

当前已完成本机生产构建、浏览器流程及真实 SQLite 备份恢复验证。以下为单台 Linux 服务器的部署方案与可调整配置示例；尚未在用户的目标内网服务器执行部署或验证网络访问范围。

## 运行方式与数据位置

- Node.js 22（至少 22.13）、pnpm 11.9；使用一个应用实例。本项目采用 `better-sqlite3`，安装原生模块应在目标系统执行，不能直接复制 macOS 的 `node_modules` 到 Linux。
- 推荐应用发布目录 `/srv/claimlist/releases/<版本>`，`current` 指向当前发布；持久数据位于 `/var/lib/claimlist/claim-list.sqlite`，与应用发布目录分离。
- 默认本地路径为 `data/claim-list.sqlite`。SQLite 使用 WAL；同目录可能有 `-wal`、`-shm` 和 `.lock` 文件。不要把它们放进 `public/`、Git、临时磁盘或共享网络盘。
- 数据目录权限建议 0700，文件 0600。应用及维护命令设置 umask 0077；数据库会保存账号邮箱、姓名、归属、认领 IP、UUID、密码哈希和会话摘要，备份同样需要访问限制。
- SQLite 连接自动执行版本化迁移。当前 `PRAGMA user_version=2`；迁移采用事务，新应用拒绝打开高于自身支持版本的数据库。后续迁移必须追加版本，不能修改已发布迁移来重建业务表。

## 配置

开发时复制 `.env.example` 到 `.env`，或通过进程环境变量提供配置。`pnpm dev/start` 和维护命令读取 `.env`。系统服务使用 `/etc/claimlist.env`。

| 变量                | 说明                                                                                                                    |
| ------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `APP_ORIGIN`        | 可选的固定浏览器来源，必须含协议且不含末尾斜杠或路径；默认空，允许使用 localhost 或本机实际网卡 IP 直连。写请求必须同源 |
| `LISTEN_HOST`       | 直接执行服务脚本时的备用监听地址，默认 `0.0.0.0`；命令行 `--hostname` 优先                                              |
| `PORT`              | 直接执行脚本时默认 1234；命令行 `--port` 优先                                                                           |
| `DATABASE_PATH`     | 推荐绝对路径，默认 `./data/claim-list.sqlite`                                                                           |
| `TRUSTED_PROXY_IPS` | 逗号分隔的代理**精确 IP**，默认空；支持 IPv4/IPv6，不接受网段。代理必须覆盖 `X-Real-IP`                                 |

`pnpm dev` 和 `pnpm start` 在 package.json 中明确使用 `--hostname 0.0.0.0 --port 1234`，优先于环境变量。systemd 示例直接运行脚本，因此读取下方环境配置；代理部署应使用该方式，或将 package.json 中的监听参数改为本机地址。

典型代理部署环境：

```dotenv
APP_ORIGIN=https://claimlist.internal
LISTEN_HOST=127.0.0.1
PORT=1234
DATABASE_PATH=/var/lib/claimlist/claim-list.sqlite
TRUSTED_PROXY_IPS=127.0.0.1
```

使用自定义 Node 入口的原因是需要可靠获取连接的客户端 IP：直连时取 socket 地址，忽略访客提供的转发头；仅当 socket 对端位于明确配置的代理列表中才读取单个 `X-Real-IP`。内部身份头每次均由入口覆盖。不要使用 `next start` 绕过入口，也不要直接向外开放受信任代理后面的应用端口。

反向代理示例见 [nginx.conf.example](../deploy/nginx.conf.example)，系统服务示例见 [claimlist.service](../deploy/claimlist.service)。替换域名、证书、Node 绝对路径和允许的**实际**内网网段，先执行 `nginx -t` 再加载配置。防火墙仅向目标内网开放入口，应用端口仅本机可访问。示例不是已完成的服务器配置。

若采用内网 HTTP 直连，直接运行 `pnpm dev` 或 `pnpm start`，通过 `http://服务器内网IP:1234` 访问，代理列表留空。`APP_ORIGIN` 可留空，此时仅认可本机实际网卡 IP / localhost 和监听端口，不接受任意 Host；也可配置固定域名来源。HTTPS 会启用 Secure 管理员及参与者 Cookie；HTTP 下 Cookie 无 Secure 属性，但仍有 HttpOnly、SameSite=Strict、管理员 24 小时／参与者 30 天固定有效期和服务端失效检查。敏感管理操作建议使用内网 HTTPS。

## 首次部署

1. 创建专用非 root 服务用户和持久目录，赋予它读写数据目录、读取应用代码的权限；配置内网 DNS、代理和防火墙。
2. 在发布目录执行 `pnpm install --frozen-lockfile`、`pnpm check`、`pnpm test`、`pnpm build`。若平台没有预构建 SQLite 绑定，需安装 Python、make 和 C/C++ 编译器。
3. 用服务用户及**同一份 DATABASE_PATH 配置**执行 `pnpm db:migrate`，然后 `pnpm setup`。后者生成随机一次性口令，数据库只保存摘要；请通过私密渠道交付管理员，不放进网页、Git 或共享日志。
4. 安装 systemd 服务与 Nginx 配置，启动单个实例。启动会持有数据库旁的进程锁，第二个实例不能使用同一数据库。
5. 从内网浏览器进入设置，凭初始化口令设置 8–128 字符管理密码。初始化完成后原口令失效，首次设置入口关闭。未初始化前再次执行 `pnpm setup` 会旋转旧口令；初始化后该命令拒绝执行。
6. 在目标网络验证允许网段可访问、范围外不能访问；至少用两台客户端检查来源 IP 传递正确，再验收认领和完成规则。不能用 robots 设置代替网络限制。

## 日常运行与重置密码

```sh
pnpm dev          # 本地开发
pnpm build
pnpm start        # 自定义入口，生产运行
pnpm reset:passwd
```

`reset:passwd` 只能在交互式终端中隐藏输入两次新密码，不接受密码参数或管道。两次一致并通过长度检查后，事务更新密码并删除所有旧管理会话；条目和认领记录保留，初始化入口不会重开。验证失败、输入不一致或 Ctrl+C 取消均不会修改旧凭据。运行命令的用户需有数据目录写权限。该操作可以在服务运行时进行；仅影响管理员，不改变参与者密码、会话或任务归属。

参与者忘记密码时，管理员在管理页的“参与者密码管理”中按邮箱或姓名查询，选择准确账号并输入两次新密码，确认重置。所有密码均为 8–128 字符，不要求组合。重置后该账号所有设备退出，新密码通过既有私下渠道交付；不提供邮件找回，也不验证邮箱所有权。

管理员初始化/登录、参与者注册、参与者登录各有独立 IP 额度，每 15 分钟最多 10 次（包括成功尝试）。参与者登录另有邮箱摘要额度，同为 10 次/15 分钟。计数存入数据库，重启不清空。共享来源 IP 共用各自额度；可信代理配置影响这一点。管理员 CLI 重置仅清理管理员限流；参与者重置仅清理目标账号限流，不清理共享 IP 限制。

## 备份

```sh
pnpm db:backup /安全备份目录/claimlist-2026-09-29.sqlite
```

命令使用 SQLite 在线备份 API，可在服务运行期间执行，生成包含所有已提交业务数据、配置、账号凭据、条目归属和两类会话的单文件一致性快照；备份以只读连接打开源库，不触发迁移；目标必须不存在，失败不会覆盖已有备份。临时文件生成成功后才改名为目标文件。不应仅在运行中复制主数据库文件而遗漏 WAL。

备份保存到独立持久磁盘，并定期复制到受控的另一台机器。建议每日及每次发布前备份，保留周期由实际运维确定。备份也包含凭据摘要和认领身份，不得放入公开下载目录。

## 恢复与演练

1. 停止 ClaimList 系统服务，确认进程退出。恢复命令检测 `.lock`，存在活进程时拒绝覆盖数据库；不应强行删除活跃锁。崩溃留下的锁仅在确认原 PID 不存在时自动清理；异常锁要求人工核对。
2. 以服务用户及正确的 `DATABASE_PATH` 运行：

   ```sh
   pnpm db:restore /安全备份目录/claimlist-2026-09-29.sqlite --confirm
   ```

3. 命令检查源文件完整性和版本，通过 SQLite 备份 API 将源写入暂存库，执行必要迁移、完整性与外键检查，并清除管理员及参与者会话/登录限制；若目标库存在，先生成 `.before-restore-<时间>.sqlite` 备份，再原子替换主库。源备份不被修改。恢复失败时不得手动删除原库，先阅读错误原因。
4. 启动应用，用恢复快照中的管理密码登录，核对清单、文案、认领和完成信息。旧管理和参与者会话全部失效，账号、密码与任务归属保留；如需改管理密码，运行重置命令。
5. 定期在隔离目录中恢复一份备份并核对条目。`pnpm test` 已自动验证备份/恢复后身份和配置保留、会话失效、再次迁移不改变业务数据。

## 发布、升级与回退

1. 在线生成发布前备份，在新发布目录安装依赖、执行检查/测试/构建。
2. 停止旧服务，使用同一持久库路径运行新版本 `pnpm db:migrate`，成功后切换 `current` 并启动；不要把空 `data/` 或测试库覆盖到持久目录。
3. 核对 `/api/list`、管理员登录和关键业务流程；验证重启后数据仍在。
4. 同数据库版本的代码回退：停机后切换到兼容代码版本。数据库发生不兼容升级时：停机、切换匹配代码，并按上述流程恢复升级前备份；此操作会丢失备份时间之后的新数据，需由维护者决定，不能自动静默回滚。

### 从匿名版 v1 升级到账号版 v2

- 使用新版 `pnpm db:backup` 先生成 v1 快照；此命令不会升级源库。停止旧服务后，再执行新版 `pnpm db:migrate`，输出版本应为 2，然后启动新服务。
- 迁移追加账号表、参与者会话表及可空条目归属字段；旧条目全字段、管理密码和管理会话保留，所有旧条目初始仍未绑定。登录时仅按当前 UUID 建立归属。
- 当前恢复命令接受 v1 和 v2：v1 在暂存库升级后恢复；v2 保留账号及归属。两种恢复都撤销两类会话。未知版本、校验失败或迁移失败均不会替换当前数据库。
- v1 应用拒绝读取 v2 库。需要回退时，应先停机，用新版恢复工具和独立 `DATABASE_PATH` 验证 v1 快照可用，然后使用兼容 v1 的旧版恢复命令将原 v1 快照恢复到实际持久路径，再启动旧应用。不要用新版恢复命令替换实际库后直接启动旧应用，因为新版恢复会将 v1 迁移为 v2。始终保留当前 v2 快照；升级后新增账号、归属和业务变更不会自动合并回 v1，回退需运维明确选择。

<a id="auth-001"></a>

## AUTH-001：共用公网 IP 可通过他人条目的完成校验

- 确认日期：2026-09-29。
- 状态：第一版已接受；后续优化候选，不阻塞研发。
- 关联需求：[浏览器身份与完成权限](product-requirements.md#6-浏览器身份与完成权限)。

### 账号增量下的适用范围

[ACC-001](account-system.md) 已实现并验收：本局限继续适用于未绑定账号的条目。已绑定账号的条目改为对应账号会话校验，不再允许通过 IP 或 UUID 放行。不能将新增账号描述为彻底解决匿名任务的共享 IP 局限。

### 当前规则

对于已经认领且尚未绑定账号的条目，只要当前请求的 IP 与认领 IP 相同，**或者**当前浏览器 UUID 与认领 UUID 相同，即允许标记完成。校验由服务器执行，姓名不作为身份凭据。

### 已知缺点与复现场景

同一公司、家庭或其他共享出口网络中的不同参与者可能拥有相同的公网 IP。IP 匹配不能证明操作者就是认领者。

当前已确认采用内网部署，面向内部开发者。内网直连时，服务器可能取得不同参与者各自的内网 IP；经共享出口或网关访问时仍可能看到相同来源 IP。实际校验使用服务器可靠取得的客户端 IP，不能假设所有内网用户共用 IP，也不能因为是内网就认为这一局限已消失。受控反向代理需正确传递来源信息，不能误将代理自身地址当作所有用户的身份依据。

例如：甲使用浏览器 A 匿名认领一个尚未绑定账号的条目，乙使用 UUID 不同的浏览器 B，但与甲共用公网 IP。乙仍然可以将甲认领的条目标记为完成。这可能导致误操作或他人代为完成，完成状态不能作为本人确认的可靠证明。

相关身份边界：UUID 标识浏览器存储，不验证真实身份；清理存储或换设备后可能丢失。如果 IP 也改变，原认领者将无法通过这两项条件完成任务。

### 接受原因

用户明确选择第一版保留宽松规则，维持无需参与者账号的简单协作流程，并要求在正式研发项目中记录这一缺点，以便后续优化。

### 后续优化候选

- 仅允许认领 UUID 匹配，由管理员处理身份丢失；需要权衡跨设备操作的不便。
- 引入独立的认领凭据或恢复方式，减少对 IP 的依赖；需要设计凭据保管与恢复流程。
- 如实际场景需要更强的身份保证，再评估参与者身份验证及其使用成本。

出现共享网络误完成反馈，或业务开始要求更准确的归属校验时，可重新评估。变更规则之前，需要明确已有认领记录如何继续使用，并同步更新需求、说明和验收用例。

### 正式研发项目交接要求

1. 将本记录迁入正式研发仓库的已知局限文档或决策记录，保留 `AUTH-001` 标识及上述背景。
2. 从研发仓库 README 或文档索引提供链接，确保后续维护者可以找到。
3. 对未绑定账号的条目保留“同 UUID 不同 IP 允许、同 IP 不同 UUID 允许、两者均不同拒绝”的验收场景；对已绑定条目按 ACC-001 验证对应账号，禁止 IP 或 UUID 回退。
4. 后续优化记录关联本条目，注明最终方案和替代版本；保留原有决策背景。
